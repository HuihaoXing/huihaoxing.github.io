Transit data pipeline · Boston University

Do weather and big events go with Green Line delays? First, three data sources had to line up.

In 30 seconds

Context
A master’s team project: do weather and big events go with longer delays on Boston’s Green Line light rail?
What I did
Built an Azure Data Factory and Spark pipeline that joins train arrivals, hourly weather and events into one table; tested the effects with a t-test and ANOVA; modeled delay with XGBoost.
Result
A 3.56-minute mean absolute error on trimmed delays. Event hours added about half a minute: significant, but small.
Limits
Trimmed delays flatter the model on the worst days; events were joined city-wide, not by distance to a stop.
Project
Master’s team project, spring 2025
Stack
Azure Data Factory, Azure Data Lake, Spark, SQL, XGBoost, Power BI
Data
GTFS schedules and actual arrivals for the Green Line B branch; OpenWeather hourly history; Ticketmaster and TD Garden event listings

01, bronze

Three feeds, three clocks.

A year of archived schedules and actual arrivals, hourly weather history and event listings, landed raw in Azure Data Lake by Data Factory and Python collectors. Arrivals stream by the minute, weather hourly, events at irregular times, each with its own keys, time zones and gaps.

02, silver

One clock.

Spark jobs parse and type every source, merge scheduled stop times with actual arrivals, and bucket every record to the hour, so a 5:42 pm arrival joins the 5 pm weather and that hour’s events.

03, gold

One table.

One row per scheduled arrival: delay in minutes, stop, direction, hourly weather and the number of events that hour. Follow one arrival in the hour highlighted in the previous step: its weather and that hour’s events join it in one row. Analysis runs on this table, never on the raw feeds.

Why a medallion architectureEach layer is a checkpoint. When a source breaks, it is repaired in bronze or silver and gold is rebuilt; downstream consumers are unaffected.

04

A model.

An XGBoost regressor predicts each arrival’s delay from 15 features: stop, direction, time, weather and events. The pairs in the scene illustrate actual delay beside the prediction in blue; they are not model output.

3.56 minmean absolute error
+0.5 minaverage additional delay in event hours

An ANOVA across weather conditions and a t-test on event hours tested each factor. The event effect was statistically significant but small.

Result

Three feeds, one reusable table.

The durable output is the table: the next question can be asked without rebuilding the joins. A model on it reached a 3.56-minute mean absolute error on trimmed delays, and events added about half a minute, so they are not the main driver of delay. A Power BI dashboard sits on the same table.

In review

What I would change.

  • Delays were trimmed with an IQR rule before modeling, so the error is measured on typical delays and flatters the model on the worst days.
  • Events were joined city-wide by hour rather than by distance to a stop, so a concert near one station counts against every station.

Both are fixable on the same gold table.
