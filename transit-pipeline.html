Case study, data engineering

Trains, weather and events run on three clocks. Can they share one?

Does weather or a big event make the Green Line late? Answering that means joining data that was never meant to meet. In a graduate team project we built the pipeline that puts all three on one clock, then measured what actually moves delays.

Project
Graduate team project, spring 2025
Stack
Azure Data Factory, Azure Data Lake, Spark, XGBoost
Data
GTFS schedules and actual arrivals for the Green Line B branch, OpenWeather hourly history, Ticketmaster and TD Garden listings

01, bronze

Three feeds, three clocks.

A year of archived schedules and actual arrivals, hourly weather history and event listings, landed raw in Azure Data Lake by Data Factory and Python collectors. Arrivals come by the minute, weather once an hour, events whenever they start. Each has its own keys, time zones and gaps.

02, silver

One clock.

Spark jobs parse and type every source, merge scheduled stop times with actual arrivals, and round every record to its hour, so a 5:42 pm arrival meets the 5 pm weather and that hour’s events.

03, gold

One table.

One row per scheduled arrival: the delay in minutes, stop, direction, the hour’s weather and the number of events that hour. Analysts query this table, never the raw feeds.

Why three layersEach layer is a checkpoint. When a feed breaks, it is fixed in bronze or silver and the gold table rebuilds; nothing downstream has to know.

04

A model.

An XGBoost model learns how stop, direction, time, weather and events move delays, then predicts each arrival’s delay from 15 features. On the right, each pair is one arrival: the real delay and the blue prediction.

3.56 minmean absolute error
+0.5 minaverage extra delay in event hours

An ANOVA across weather conditions and a t-test on event hours tested each factor. The event effect was significant but small.

Result

One delay table, 3.56 minutes of error.

The answer is modest and useful: events add about half a minute, so they are not where delay mostly comes from. The lasting result is the table. The next question can be asked without rebuilding the joins.

In review

What I would change.

  • Delays were trimmed with an IQR rule before modeling, so the error is measured on typical delays and flatters the model on the bad days that matter most.
  • Events were joined city-wide by hour rather than by distance to a stop, so a concert near one station counts against every station.

Both are fixable with the same gold table.
